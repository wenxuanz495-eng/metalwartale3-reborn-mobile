# SOL 存档修改经验与错误解决总结（4.0 本地版实测）

> 整理日期：2026-09-11
> 来源：4.0 星座武器存档注入任务（含一次"数据处理中"卡死事故的完整排障记录）。
> 适用范围：4.0 本地版及同代（SOL 存档 + AMF3 载荷）的存档读取、修改、注入；11.3 线的
> `game_save.bin`（同为 writeObject+deflate 载荷）编解码原理相同，仅外壳不同。
> 工具：`tmp-soya-family-test\4.0-localize\soltool\`（Go，复用主仓库 `server\amf.go` 编解码器）。

---

## 一、先记原则（本次事故换来的）

```text
1. 改存档 ≠ 改字节就完事——每个自描述结构的"长度/引用头"都要随数据一起重算；
   只换内容不改头，Flash 读到截断流就抛异常，表现是"数据处理中"永久卡死。
2. 改存档前游戏必须完全退出（含后台挂着的实例）——游戏会以内存态覆盖写回 SOL，
   任何磁盘上的修改都会被一次自动存档冲掉。
3. 先 .bak 后动手；注入前游戏未关 → 先杀进程再注入。
4. 注入后必须"字节级回读 + 实机读档"双重验证，缺一不可。
5. 工具回读成功 ≠ 游戏能读——解压器/编解码器和 Flash 的实现差异本身就是坑源。
```

## 二、SOL 文件实测格式（逐字节，与常见文档描述有出入）

以 `yagao.sol`（Flash Player 实际写出的文件）为准：

```text
偏移   长度  内容
0      2    00 BF                         魔数
2      4    u32 BE = 文件总长 - 6         长度字段（不是总长本身！）
6      4    "TCSO"                        签名
10     6    00 04 00 00 00 00             保留（04 疑似格式版本）
16     2    u16 BE = 根名长度             如 05
18     N    根名（如 "yagao"）
+N+18  4    u32 BE = 对象编码（3 = AMF3） ← 常见文档常漏记这个字段
之后   ..   记录流（本游戏只有一条）：
            AMF3 字符串名（u29 头 + 字节，无类型标记）如 03 61 = "a"
            AMF3 值 = 0x0C（ByteArray 标记）
                     + u29 = (字节数 << 1) | 1   ← 内联标志在低位！
                     + 字节数那么多的 raw deflate 流
                     + 0x00 填充字节（每条记录后一个）
```

载荷 = `ByteArray.writeObject(GameData)`（AMF3）+ `ByteArray.deflate()`（raw deflate，无 zlib 头）。

**u29 实例**：`E1 77` → 解码 `((0xE1 & 0x7F) << 7) | 0x77 = 12535` → 真实字节数 = `12535 >> 1 = 6267`，低位 1 = 内联（非引用）。写回时反向：`v = (新字节数 << 1) | 1`，若 v < 0x4000 用两字节 `0x80 | (v >> 7)`、`v & 0x7F`。

**编码字节数 ≠ 文件剩余长度 ≠ 解压后长度**，三者是三个不同的数，别混用。

## 三、本次踩的坑与解决方法

### 坑 1（事故主因）：只换 payload 不改 u29 长度头 → "数据处理中"卡死

- **现象**：注入后点继续游戏，"数据处理中"永久停留，游戏挂后台无响应。
- **根因**：ByteArray 的 u29 长度头保留了旧值（6267），新 payload 6892 字节。Flash 按旧长度
  只读到截断的 AMF3 流 → `readObject` 抛异常 → 加载中断。
- **解决**：写回时按新 payload 长度重写 u29（工具 `patchU29Length`）。
- **验证**：字节级回读（u29 解码 = 新长度 ✓ → raw deflate 全量解压 ✓ → AMF3 首字节 0x0A ✓）→ 实机读档 ✓。
- **教训**：自描述结构里"长度字段"是数据的一部分；改数据必改头。回读验证只做解压不够，
  要把 u29/魔数/终止符逐项核对。

### 坑 2：载荷里有 NaN，Go 编码器直接拒绝

- **现象**：`encode: MCoin: NaN and Infinity are not valid save values`。
- **根因**：4.0 新档 `MCoin` 存的就是 NaN（字符串型后备字段空串转数字的产物，即舰桥 M币
  显示 NaN 的根源），而主仓库编码器为防坏档明确拒绝 NaN。
- **解决**：编码前递归归一化 NaN → 0（与 11.3 离线版"M币 NaN 自动归零"同款处理）。
- **教训**：跨版本搬字段值前先看它是不是合法数字；显示层的 NaN 不代表可以原样序列化。

### 坑 3：SOL 头布局照抄文档 → 解析失败

- **现象**：按"常见文档"的偏移解析报 `not a SOL file`。
- **根因**：实际文件多了 u32 编码版本字段、长度字段语义是"总长-6"，文档多为准。
- **解决**：以真实文件逐字节 dump + 暴力试探记录起点，实证出布局后再固化进工具。
- **教训**：逆向二进制格式，实证 > 文档；一切以"能自洽走完整个文件"为准。

### 坑 4：卡死会话的进程还挂在后台

- **现象**：修好存档后用户后台仍有一个卡死实例（PID 存活）。
- **风险**：该实例内存里是坏档会话，若触发任何写回会把修好的存档再次覆盖成坏档。
- **解决**：注入前 `tasklist` 查 FlashPlayer，有则先结束；交付用户前确认无残留进程。

### 坑 5：调试工具自身的不靠谱

- 验证脚本 JSON 解析连续失败，实为工具输出截断上限（6000 字符）没放开——**先怀疑自己的
  验证工具，再怀疑被验证对象**。
- LF 换行的 BAT 在 cmd 下解析错乱、Git Bash 环境的 `timeout` 会顶掉系统 `timeout`——
  交付 BAT 一律 CRLF + `ping` 延时。

## 四、4.0 存档字段速查（weapons 相关）

```text
根对象（writeObject 的 GameData）
├── GCoin / MCoin（Number 访问器，后备 String 防大数）+ 镜像 GCoin2 / MCoin2
├── armsItems
│   ├── armsState        8 装备槽解锁状态（"" 解锁 / "lock"）
│   ├── arr              背包武器条目数组（bagMaxNum = 30）
│   ├── equArr           已装备实例（与 arr 同构，装备时复制）
│   ├── equMaxNum        8
│   └── lastID           新条目 id 计数器（数字）
├── giftData             haveConB 等；4.0 无 conClaimed 存档字段（UI 运行时态）
└── levelsLock / nowDifficult / nowGameLevel / playerName（默认 "4399小战士"）
```

**武器条目字段**（克隆模板实证）：`add / addSelf / baseEnergy / baseEnergyRate / baseLabel /
buyDate / chipHole / cnName / color / define(null) / dpsHurt / exploreIndex(-1) / holeArr /
id(String!) / imgLabel("arms/xxx_lv1") / maxEnergy / maxEnergyRate / maxHoleNum / name /
newB / nowEnergy / nowHoleNum / site / strengLevel / type / type2`。

**注入要点**：
- 模板克隆（json 深拷贝现有条目）+ 只覆盖身份五件套：`baseLabel / imgLabel / name / cnName / id`，
  另给 `site`（唯一空位）、`newB=true`，`lastID` 顺延——不要手搓新对象，模板保证 schema 兼容。
- 武器 baseLabel = `定义id + "_lv" + 等级`，游戏按 `getAD_byStr`（split "_lv"）反查定义；
  查不到 → `getArmsDefine()` 里 `d0.itemsData = this` 空引用 → 就是"数据处理中"卡死。
- 反作弊（4.0 原版 zuobiTest）已在本地版补丁中禁用；未禁用的版本注意经验/积分比与物品数量校验。

## 五、标准流程（以后照此执行）

```text
① 确认游戏完全退出（含后台实例）
② 备份 .sol → .bak
③ soltool inspect 读存档，确认目标字段与模板条目
④ 修改（模板克隆 + 身段覆盖 + lastID/site 顺延 + NaN 归一化）
⑤ encodeGamePayload 重编码 + 重写 u29 长度头 + 重建 SOL（u32 长度字段同步）
⑥ 字节级回读：u29 解码 = 新长度 / deflate 全量解压 / AMF3 首字节 / 终止符
⑦ 实机读档：进游戏看数据 → 再点一次"保存存档"让游戏写回，排除"只读不写"的假成功
⑧ 归档 MD（本文件所在目录）
```

## 六、证据等级

- A：SOL 布局、u29 编码、字段结构均有真实文件逐字节验证；事故根因有修复前后对比。
- B：Flash 读取端对 u29/填充的容错边界未做穷举测试（只验证了正确路径）。
