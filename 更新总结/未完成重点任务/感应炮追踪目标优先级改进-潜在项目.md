## 一、背景与现状（已逐字核实的代码事实）

感应炮爆能弹 `followB=3 / followDelay=1000 / bulletSpeed=2 / bulletLife=8`，当前追踪链路：

1. **目标分配**（`BodyGroupRefresh.as`，每帧）：对 `followB > 0` 且 `targetBody == null` 的我方弹，调用 `getHurt_RandomEnemy()` = `getHurt_Arr2(enemy_arr)` 过滤（`hitHurtB == 0` 且 `img.visible`）后**随机抽一个**存活敌人。
2. **追踪执行**（`OneBulletBody.followTarget`，每帧）：`followDelay=1000` 触发低速瞄准分支——弹速 2 < 5 时每帧 `mot.ra = atan2(目标当前位置)` + `a0=4` 加速（上限 bulletMaxV=30）。
3. **死分支**：目标死亡换目标/清目标的代码在 `live_t >= followDelay` 分支内，`followDelay=1000` 按秒比较、弹最多活 8 秒 → **该分支永不执行**。后果：目标一旦锁定，死后不清除、不重新分配，弹围着尸体坐标打转直到自毁或撞上其他敌人（碰撞对任何敌人生效）。
4. 分配代码为**所有 followB>0 弹共用**：感应炮 + 守望者（lightningBall）等追踪弹。

用户实测观察与此完全吻合（全场弹追第一个怪、目标死亡不转火）。

## 七、精英/冠军/Boss 识别方式（2026-09-06 代码核查结论，只读未修改）

游戏自身提示文本（`dataMust\scripts\gameAll\define\TipsDefine.as`）："机器人可以分为普通怪、精英怪、稀有怪和BOSS四种，精英怪拥有蓝色外形和蓝色名字，稀有怪拥有金色外形和金色名字，BOSS拥有紫色名字。"——**用户所称"冠军怪"即代码中的 `champion`（提示文本叫"稀有怪"，金色）**。

### 识别方式：敌人 body 实例上的 `type` 字段

- 所有敌方 body 类（EnemyHeroBody、ChargerBody、CutterBody、AirLaserFortBody、AlarmTowerBody、AtomicTowerBody、BansheeFighterBody 等）统一声明 `public var type:String = "soldier"`。
- 取值与含义：

| type 值 | 中文 | 外观标志 | 生成方式 |
|---|---|---|---|
| `"soldier"` | 普通怪 | 无 | 默认值 |
| `"super"` | 精英怪 | 蓝色（`superEnemyColor`） | 出怪时 4% 概率升级（EventGroup.as:1372，需 isSuperB 名单通过、非首关包等条件）；精英单位还会召唤 2 只伴生 super（superNum 计伴生数） |
| `"champion"` | 冠军怪（=稀有怪） | 金色（`championEnemyColor`） | 出怪时 1% 概率升级（EventGroup.as:1366）；`championAllRa` 数值倍率 |
| `"boss"` | Boss怪 | 紫色名字 | 关卡脚本/EventOrder 直接指定（ArenaLevel.as:116 等）；置 `define.isBossB = true` |

- 配套标志：`EnemyDefine.isBossB`（boss 置 true）；`EnemyDefine.superNum`（精英伴生数量，0 = 本体）。
- 升级逻辑位置：`EventGroup.as` 1340–1475 行段（bodyAdd 出怪流程），BOSS 触发 `bossShowB`、掉落药箱等全局处理在 1475/1575 行。
- 敌人当前血量：`b0.define.nowLife`（`EnemyDefine` 继承 `LifeBodyDefine`，同文件 162 行有 `getLifePer()` = nowLife/maxLife）。

### 对未来实现的结论

目标选择时直接读 `b0.type` 即可做四级优先级（boss > champion > super > soldier），同级内取 `define.nowLife` 最小者——**全部字段在 body 实例上现成可读，无任何启发式**，实现难度与预估一致（低）。

## 九、激光视觉机制区分（感应炮 vs 其他激光类武器，已代码核实 + 用户实机截图佐证）

> **勘误（2026-09-06，用户实机截图佐证）**：感应炮激光**并非隐形**。它有一条可见的**橙红→黄渐变细线**（用户截图：细线横贯屏幕，一端红、渐变到黄，末端为命中闪光）——这条线就是**本体动画内的渐变光束条**（shape 416/417，703×4px，红→黄渐变，随攻击周期逐帧显示）。此前"隐形射线"的表述不准确：**射线判定本身无贴图，但动画光束条提供了可见的激光线**，应表述为"判定隐形、动画显形"。

### 9.1 感应炮激光的可见画面构成（修正后）

1. **渐变光束细线（激光主体的可见形态）**：本体动画第 5～7 帧放置的 shape 416/417（703×4px 渐变条，lv1/lv2 纵向缩放 0.5、lv3 纵向 0.75、lv4 原始），每次攻击周期随动画显示——实机观感即用户截图中的橙红渐变细线。三版美术逐字节一致（已验证）。
2. **命中特效**：命中点放置旋转对齐弹道的六帧能量爆散（41–90px 带方向拖尾，已按 2.5 还原）+ 2.5 音效。
3. **射线判定本身无贴图**（`LaserBody(false)`，induction_1 无 bulletImgLabel）——但"无弹体贴图"不等于"激光不可见"。

### 9.1.1 渐变线的实现方式（2026-09-06 决定性验证：美术素材，非代码绘制）

**用户假设**：渐变线由代码决定（固定距离的放射射线，类似射线 UI）。

**验证结论：由美术素材决定。** 代码全量搜索无任何矢量画线逻辑（`lineStyle/lineTo/lineGradientStyle` 零命中）。该线是**预绘渐变条 shape 416/417（703×4px， olive→橙→红）**，放置于本体动画第 5/6 帧、**炮口前方 x≈66→769px 处**（与炮管同高，translate(-560,160)twips + scale(1,0.5)，内容定位精确换算），随武器瞄准方向整体旋转。

**逐帧合成渲染**（FFDec 导出形状 + 按矩阵合成，见 `induction_anim_frames.png` 临时目录）与用户实机截图完全吻合：炮口 → 黄/橙 → 远端红色，约 703px 固定长度。

**"射线 UI"观感的来源**：因为它是动画里的**固定长度美术条**——无论敌人远近、有无命中，每次攻击周期都显示同样长的线，不会在敌人处截断（用户截图中线穿过敌人上方继续延伸正是此因）。真正的命中是隐形射线（激光首发）与爆能弹的碰撞判定。故"像固定距离放射射线"是**观感**，实现上是固定长度美术。

### 9.1.2 经验沉淀：SWF 内"细线/光束"的分析方法（矢量图判定 + 坐标换算）

**结论**：感应炮激光渐变线是 **DefineShape 矢量图形**（渐变填充矩形），不是位图（DefineBits）。矢量图特性：任意缩放不失真、体积极小（703px 渐变线仅约 1–2KB）、FFDec 导出 PNG 只是栅格化快照。

**本次沉淀的通用分析流程**（判定"游戏内某条线/光斑从哪来"）：

1. **判定类型**：FFDec swf2xml 后按标签分类——`DefineShape?Tag` = 矢量图（描边/渐变填充），`DefineBits*Tag` = 位图（有 bitmapWidth/Height），`DefineMorphShapeTag` = 变形图形（ratio 推进）。三类渲染特性和验证方式完全不同。
2. **位置计算（易错点）**：`PlaceObject2Tag` 的 matrix `translateX/Y` 单位是 **twips（20 twips = 1 px）**，不是像素。内容在父 Sprite 中的像素位置 = `translate + shapeBounds.Xmin/20 × scaleX`（Y 同理带 scaleY）。本次曾把 twips 直接当像素，位置错 28 倍，导致误判"光束条在本体后方"——凡坐标异常先检查单位。
3. **视觉验证（不依赖实机）**：`ffdec -format shape:png -export shape` 导出各形状 PNG（PNG 尺寸 = shapeBounds 框），再按第 2 步的矩阵手动合成到父 Sprite 坐标系逐帧出图，与实机截图比对。本次合成渲染的 f5/f6 帧与用户截图完全吻合，一次性定案。
4. **排查顺序模板**：配置弹体贴图（bulletImgLabel）→ 动画帧内容（矢量条/位图/变形）→ 代码画线（lineStyle/lineTo，本项目为零）→ 遮罩拉伸（MaskArmsImage 类）→ 命中特效旋转贴附。逐层排除即可定位任何"游戏内线条"的来源。

### 9.2 与其他激光类武器的机制区分

| 激光类武器 | 光束美术 | 可见机制 |
|---|---|---|
| **感应炮**（主武器，penetrationB=1） | **本体动画内的渐变光束条**（416/417，703×4px）+ 命中特效方向拖尾 | 光束条作为**动画帧内容**直接显示（无遮罩、不随命中距离拉伸）；命中判定为射线-矩形检测（`hitRectLine2`） |
| **战殇 laser / 炽天使 hotline**（副武器，penetrationB=0） | **独立光束美术图**（652.jpg 蓝白 / 750.jpg 橙色多线，约 1000px 预置于武器动画） | **渐变光束美术 + 矩形遮罩（MaskArmsImage）**：遮罩宽度按"炮口→命中点"距离设置（`arms.length = imgLen`，无命中全开 1000），形成贯穿屏幕的宽光束 |
| 敌方激光台（AirLaserFort 等） | 同副武器体系 | 同上 |

关键区别一句话：**副武器激光是"先画长光束、用矩形遮罩裁出可见长度"（宽光束）；感应炮激光是"动画帧内固定渐变细线 + 命中点旋转爆散"（细线）**。两者代码分支（penetrationB 0/1）、图像类（MaskArmsImage/ArmsImage）、可见机制均不同，但**都有可见的渐变光束美术**——三版（2.5/3.4/GitHub）美术完全一致，无需迁移。

**结论：逻辑1 完全可实现，识别标志明确且互不重叠（类判断 + type 字段 + nowLife），无启发式。** 实现 = 把 `BodyGroupRefresh` 分配点的 `getHurt_RandomEnemy()` 替换为按上述层级的遍历选择函数；**前置依赖：必须同时实施"目标死亡→清空 targetBody"（8.1 方案甲），否则优先级只对新建弹生效，已锁死弹不会转火**。

### 10.4 需用户确认的设计缺口
