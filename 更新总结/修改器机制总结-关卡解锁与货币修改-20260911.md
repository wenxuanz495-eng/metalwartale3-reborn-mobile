## 一、修改器架构（先记这一条）

修改器不是独立的作弊程序，而是**直接编辑权威存档 JSON 的网页工具**，与游戏共用同一个 Go 后端和同一份存档：

```text
修改器.bat → build/server.exe → 浏览器打开 modifier.html
   ├─ modifier.html（增强壳）：iframe 加载服务端基础修改器页
   │    └─ 注入"定制车辆 / 定制武器 / 特殊功能 / 芯片洗练"页签（字符串替换，modifier.html 第 283~302 行）
   ├─ 基础修改器（server/editor_page.go，"常用/材料与芯片/全部字段/原始JSON/备份恢复"）
   └─ 全部读写都走同源接口：
        GET  /api/editor/data   读权威存档（AMF→JSON）
        POST /api/editor/save   写回（JSON→AMF，见第四节保存链）
```

关键前提：**游戏的作弊旗标本身就是存档字段**。`GameData` 定义了 8 个 `mod*` 布尔字段（GameData.as 第 189~203 行），读档时直接从存档 obj 恢复（第 380~405 行）。所以修改器"开功能"＝往存档里写布尔值，游戏读档后自动生效。

| 旗标（存档字段名） | 修改器界面名 | 作用 |
|---|---|---|
| `modInfiniteEnergy` | 无限能量 | 战斗能量不减 |
| `modGod` | 车身无敌 | `GameData` 受伤入口 `if(this.modGod && value < 0)` 拦截（第 844 行） |
| `modOneHit` | 一击必杀 | |
| `modUnlockAll` | 关卡全解锁 | 见第二节 |
| `modAllLevelsPassed` | 所有关卡通关 | 见第二节 |
| `modCraftFree` | 研发无视全部条件 | 见第三节（跳过材料需求） |
| `modNoExtraCooldown` | 副本挑战无冷却 | 保存时清冷却时间戳数组 |
| `modNoTaskCooldown` | 任务无冷却时间 | 同上 |
| `disableAutoCollectLifePer` | 禁止自动捡取医疗箱 | |

## 二、解锁全部关卡：两条路

### 2.1 旗标法（modUnlockAll / modAllLevelsPassed）

游戏侧所有关卡锁定判定都先问这两个旗标（`GameData.as`）：

```actionscript
public function getLevelUnlockB(diff0, level0, levelPack0="") : Boolean
{
   if(this.modUnlockAll || this.modAllLevelsPassed) return true;   // 第 1077 行
   ...  // 原版逻辑：按 levelsLock[难度] / knowingData / ghostData 判定
}
```

- `getNowLevelUnlock()` / `getKnowingLevelUnLock()` / `getGhostLevelUnLock()`：旗标开启时返回 `9999`（第 666~682、1071~1075 行）；
- 星级评定同步生效：`NewLevelData.getScore()` 旗标开启时直接返回 `10000`（满分），`plusAllStar()` 返回全部星星（NewLevelData.as 第 194、224 行）。

修改器入口："特殊功能"页签勾选 → `saveSpecialFeatures()` 把布尔值写入当前槽 `data` 后调 `/api/editor/save`（modifier.html 第 405 行）。

### 2.2 剧情进度法（真实进度改写，不开作弊旗标）

"特殊功能"页还有"剧情进度"下拉（自由之心 170 关全表内置在 modifier.html 第 151 行 `freeHeartLevels`）。选择"已通关到：第 X 关"后 `applyStoryProgressToLevel()`（第 183~223 行）做**真实的进度改写**：

1. `newLevelData.p1.lockNum = 已通关关号 C + 2`（原版规则：通关 C 解锁 C+1，可进入到 C+1 意味 lockNum=C+2；最终关则 C+1）；
2. `scoreObj` 补写 `p1_0_0~p1_0_C` 的通关分数记录（第一关 1 分占位，其余 10050），并清理超出进度的分数；
3. `d.levelsLock = [1,0,0,0,0]`（四个难度的主线锁定表复位为初始可进状态）；
4. **强制 `modUnlockAll = modAllLevelsPassed = false`**（第 216~217 行）——这条路刻意不依赖作弊旗标，让进度与"正常玩出来的存档"结构一致，避免旗标副作用污染后续判定。

### 2.3 冷却类旗标的连带清理

勾选"副本挑战无冷却/任务无冷却"保存时，除写旗标外还把存档里的**冷却截止时间戳数组清零**，保证立即生效而不是等时间戳到期（modifier.html 第 405 行尾部）：`extraData.cooldownReadyAt`、`weekExtraData.arr[].readyAt`、`specialExtraData.readyAt`、`challengeTaskData.taskReadyAt`、`taskData.slotReadyAt` 等。

## 三、跳过材料需求：modCraftFree（研发无视全部条件）

**代码锚点**：`GameData.as`、`GoodsItemsDataGroup.as`、`UI/research/ArmsResearchUI.as`

### 3.1 查询侧：材料永远"够"

```actionscript
public function getNumByBase(str0:String) : int
{
   if(Game.gameData.modCraftFree && this == Game.gameData.materialsItems)
   {
      return 9999;   // GoodsItemsDataGroup.as 第 445 行
   }
   ...  // 正常查询背包数量
}
```

注意条件是 `this == materialsItems`：只有**材料背包**被"注视为无限"，道具背包（propsItems）不受影响——所以精英挑战卡等道具不会被误判。

### 3.2 消耗侧：材料永不减少

`useItemsNum()` / `useItemsData()` 在 `modCraftFree` 且来源是材料背包时直接 `return true` / `return`，不扣数量（GoodsItemsDataGroup.as 第 473~476、509~512 行）。

**安全阀**：`useItemsNumReal()` / `useItemsDataReal()` 会临时把旗标关掉执行真实扣除再恢复（第 464~470、499~506 行）——需要"真实消耗材料"的少数逻辑走 `_Real` 通道，防止无限材料把某些消耗性流程弄坏。

### 3.3 研发界面：需求图标全绿

`ArmsResearchUI.as` 第 994 行：研发所需材料（`mustItemsBox`）在旗标开启时 `setCondition(1)` + `setMustNum(9999, nowNum)`——界面显示"需求 9999 / 拥有足够"，全部条件满足。

### 3.4 读档时的状态补齐：completeModCraftResearch()

开旗标的存档每次读档时（`GameData.inData_byObj` 第 514~518 行）自动执行 `completeModCraftResearch()`（第 540~559 行）：

- 解锁全部 8 个主武器槽 + 全部副武器槽（`unlockSite`）；
- 全部玩家技能升到满级——**唯独跳过 `jump`（反重力装置）**，源码注释明确："反重力装置是正常玩家升级，研发作弊不得改动其存档等级"。

## 四、货币修改：主字段 + 镜像字段同步

### 4.1 修改器入口

基础修改器"常用"页的"货币"卡片提供 `GCoin`（G币）/ `MCoin`（M币）两个数字输入框（editor_page.go 第 72~74 行），卡片标题注明："**备用字段保存时自动同步**"。

### 4.2 为什么要同步：存档里有成对的镜像字段

游戏侧 `GameData` 除了 `GCoin`/`MCoin` 还有 `_GCoin2`/`_MCoin2`（第 99、103 行），是**原版遗留的冗余镜像字段**：

- 读档：`GCoin2 = obj.GCoin2（没有就取 GCoin 兜底）`（第 377~378 行）；
- 游戏内每次加减币都会把镜像刷成主字段：`addCoin()` / `addMCoin()` 末尾 `this.GCoin2 = this.GCoin`（第 944~960、983~995 行），并且原版逻辑里计算了局部变量 `zuobi0 = (g1 != g2)`——即"主/镜像不一致"在原版语境下是作弊检测的痕迹（反编译范围内该变量只计算未强校验，属遗留代码）。

因此修改器若只改主字段，`GCoin2/MCoin2` 会变陈旧值，主/镜像不一致，老存档诊断困难。**服务端在保存时强制对齐**：

```go
// editor.go 第 376~416 行 normalizeCurrencyMirrors()
if primary, exists := data["GCoin"]; exists { data["GCoin2"] = primary }
if primary, exists := data["MCoin"]; exists { data["MCoin2"] = primary }
// 对 8 个存档槽逐一执行；主字段为权威，镜像永远跟随
```

### 4.3 数值边界（游戏侧）

- `addCoin()`：G币负值归零、上限 2,000,000,000（防 32 位溢出）；`addMCoin()`：M币负值归零。
- 修改器直接写字段值，同样受读档后的游戏逻辑约束；此前公告过的"M币 NaN 自动归零"兜底也在。

### 4.4 保存链（所有修改共用，不止货币）

`POST /api/editor/save`（editor.go 第 297~370 行）按序执行：

```text
1. normalizeEditedValue()   以当前存档为模板逐节点校验类型/结构（拒绝改结构、改类型）
2. normalizeAMFArrayMaps()  AMF 稀疏数组/密集数组形态归一（$dense）
3. normalizeCurrencyMirrors()  GCoin→GCoin2、MCoin→MCoin2 强制同步（8 槽）
4. validateCarLevelLimits() 车辆等级上限校验
5. validateEditorValue()    数值合法性校验
6. encodeGamePayload()      JSON → AMF+deflate
7. parseGamePayload() 回读  写入前自检（编码后能完整解码）
8. createEditorBackup()     自动备份当前存档（before-edit，保留最近 20 份）
9. savePrimary()            原子替换写入 game_save.bin + yagao.json 导出 + SQLite 历史
```

任何一步失败即整体拒绝，不会写出半套坏档。
