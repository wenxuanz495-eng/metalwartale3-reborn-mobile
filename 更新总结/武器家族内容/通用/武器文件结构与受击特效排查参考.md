# 武器文件结构与受击特效排查参考

日期：2026-09-04

## 文档用途

本文用于记录目前已经验证过的武器文件结构、视觉特效调用关系，以及后续寻找其他武器受击特效时应采用的排查方法。

本文只讨论视觉表现相关内容，包括：

- 武器本体、炮口和发射表现；
- 子弹飞行表现；
- 子弹命中敌人或墙壁后的受击表现；
- 蓄力、后坐力、帧数、矩阵和图层调用；
- 公共特效与武器独立特效的归属关系。

本文不讨论伤害、等级、研发材料、研发要求、价格、能量消耗等实际游玩参数。

## 一、武器视觉调用的基本结构

一个武器家族通常由“家族定义—形态/等级—视觉调用—SWF 资源”几层组成。排查时不能只看中文名称，也不能只看某个文件名是否相同。

可按下列关系理解：

```text
武器家族 ID
  → 具体形态或等级配置
    → imgLabel / bulletImgLabel / hitImgLabel 等视觉字段
      → father 或资源组路径
        → 对应 SWF
          → SymbolClass / Export 名称
            → Character ID
              → DefineSprite / DefineShape / Bitmap
                → 时间轴帧和嵌套资源
```

### 常见视觉字段

| 字段 | 主要用途 | 排查重点 |
|---|---|---|
| `father` | 指示配置继承关系或所属资源/武器体系，具体含义需结合所在配置结构判断 | 不要仅凭字段名推断最终资源 |
| `imgLabel` | 武器本体、炮口或发射主体相关的视觉调用 | 检查是否复用上一级形态，及其所在 SWF |
| `bulletImgLabel` | 子弹飞行、子弹主体或子弹附属表现 | 检查子弹本体、尾迹、嵌套 Sprite 和帧数 |
| `hitImgLabel` | 子弹命中目标后产生的受击/死亡判定表现 | 这是定位受击特效的首要入口 |
| `bulletLink` | 某些武器中用于关联子弹配置或子弹对象 | 需要和 `bulletImgLabel` 分开核对 |
| `bulletVra` | 子弹自转等视觉参数 | 可以单独保留，不应因资源导入而自动改动 |
| 后坐力字段 | 发射时武器或炮口的视觉位移表现 | 属于可参考、也可按项目策略忽略的视觉层 |

字段的实际作用可能受到父级配置、运行时代码和资源命名规则影响。因此最终判断必须回到实际加载的资源和游戏画面，而不是只依据 XML 字段名称。

## 二、如何定位受击特效

这里的“受击特效”专指：子弹打到敌人或墙壁，判定产生命中/死亡效果后显示的视觉效果，不是子弹飞行特效，也不是炮口闪光。

推荐按以下顺序排查：

```text
1. 找到具体形态的武器配置
2. 读取该形态的 hitImgLabel
3. 沿 father / 资源组规则解析实际 SWF
4. 在 SWF 中查找对应的 Export / SymbolClass
5. 确认 Character ID 和定义类型
6. 展开 DefineSprite 的全部时间轴帧
7. 递归检查嵌套 Sprite、Shape、Bitmap 和 Sound 引用
8. 导出每一帧进行视觉对比
9. 用哈希和回读结果确认来源是否真的一致
```

### 必须区分的三种表现

| 表现 | 发生时机 | 常见定位方式 |
|---|---|---|
| 炮口/发射特效 | 武器开火瞬间 | `imgLabel`、发射时间轴、炮口图层 |
| 子弹飞行特效 | 子弹飞向目标的过程中 | `bulletImgLabel`、子弹 Sprite、尾迹时间轴 |
| 受击特效 | 子弹命中敌人或墙壁后 | `hitImgLabel`、`motion_hit_effect` 或对应独立资源 |

如果游戏中受击画面没有变化，优先检查 `hitImgLabel` 实际指向的资源，而不是继续检查子弹图片或炮口图片。

## 三、公共特效与独立特效

武器名称不一定等于特效资源的归属。多个武器可能调用同一个公共资源；同一个家族的不同形态也可能分别调用独立资源。

### 公共特效

公共特效通常位于公共资源组，例如 `sub`。多个武器配置可以写入相同的调用：

```text
hitImgLabel = sub/motion_hit_effect
```

运行时还可能按照规则补充随机后缀，最终使用：

```text
sub/motion_hit_effect_1
sub/motion_hit_effect_2
sub/motion_hit_effect_3
sub/motion_hit_effect_4
```

因此，发现多个武器使用同一个 `hitImgLabel` 时，应先认定它们存在公共依赖，再确认是否有形态级覆盖，不能把该特效直接标记为某一个武器专用。

### 独立特效

独立特效通常有专属的 Export 名称、资源路径或 Sprite 定义。判断其是否真正独立，需要同时满足：

- 配置调用不同，或运行时明确选择了不同资源；
- 对应 SWF 中的资源定义不同；
- 导出的帧图或像素内容确实不同。

仅仅出现不同的 Character ID，不足以证明是不同视觉资源；反过来，文件名相同也不代表文件内容相同。

## 四、已确认案例

### 1. 2.5 版本的小黄豆与火神炮

目前已核实，小黄豆家族和火神炮家族在 2.5 版本中共用同一组公共受击特效：

```text
hitImgLabel = sub/motion_hit_effect
```

实际运行时表现为 `sub/motion_hit_effect_1～4` 四种静态变体。这说明“公共受击特效”可以被多个武器家族共同使用，不能按武器名称建立一对一映射。

### 2. 仓库小黄豆覆盖前的旧版调用

当前 GitHub 仓库在覆盖 2.5 公共特效以前，小黄豆使用的是：

```text
hitImgLabel = bullet/yellow_motion
```

它位于：

```text
bullet.swf → yellow_motion
Character ID = 103
```

已知 3.4 版本与当前 GitHub 版本的 `bullet.swf` 文件哈希完全一致：

```text
SHA-256 = 265D97F1DD8E1C14194A3BDD7F7F5FBAC1EA8399ABEF15F57993FC7E60E53B9F
```

`yellow_motion` 时间轴共有 4 帧，其中第 1～3 帧为可见表现，第 4 帧是移除对象后的透明结束帧。这个第 4 帧不能误判为多余的可见特效帧。

### 3. 两套调用不可混淆

```text
bullet/yellow_motion
```

与：

```text
sub/motion_hit_effect_1～4
```

属于不同资源组、不同表现体系。前者是仓库旧版小黄豆调用，后者是 2.5 小黄豆和火神炮共用的公共受击特效。

## 五、SWF 结构检查重点

### 1. 不要只看导出名称

同一个名称可能在不同 SWF、不同版本或不同资源表中对应不同内容。至少需要记录：

```text
资源路径
SWF 文件哈希
Export / SymbolClass 名称
Character ID
定义类型
时间轴帧数
每帧可见对象
嵌套引用
```

### 2. 不要只看 Character ID

Character ID 只是 SWF 内部索引。不同版本可以重新分配 ID；同一个数字在不同文件中也可能对应不同类型，甚至可能出现 `DefineShape`、`DefineSprite`、`DefineSound` 等类型冲突。

正确做法是记录：

```text
旧 ID + 定义类型 + 所在文件 + 引用关系
```

之后再判断是否可迁移、是否需要重新分配 ID。

### 3. 时间轴必须递归展开

检查一个受击或发射特效时，不能只导出根 Sprite。应检查每一帧中的：

```text
PlaceObject
RemoveObject
ShowFrame
矩阵
颜色变换
深度
嵌套 Sprite
Shape 的位图填充
声音引用
```

如果只收集根节点或直接子节点，可能出现“工具回读成功，但游戏缺少闪光、尾烟、命中特效或清理帧”的假成功。

## 六、帧数判断方法

“总帧数”与“可见画面帧数”不是同一个概念。判断是否存在多余帧时应分别记录：

| 项目 | 含义 |
|---|---|
| 时间轴总帧数 | SWF 时间轴定义的全部帧数 |
| 可见帧数 | 至少有可见对象或有效像素的帧数 |
| 清理帧 | 用于移除对象、结束显示或等待状态的帧 |
| 静态变体数 | 同一调用规则下的不同资源变体数量 |

例如，`yellow_motion` 的第 4 帧虽然没有新增可见图像，但承担结束和清理作用，不能据此认定它是“多出来的一帧”。

比较 2.5、3.4 和 GitHub 版本时，必须逐帧查看：

```text
帧数是否一致
每帧是否存在对象
对象是否只是清除
对象的 Bitmap / Shape 引用是否一致
矩阵、缩放、透明度、颜色变换是否一致
```

## 七、后续寻找其他武器受击特效的标准流程

### 阶段 A：配置定位

1. 按武器家族和具体形态列出配置条目；
2. 记录该形态的 `hitImgLabel`；
3. 记录 `imgLabel`、`bulletImgLabel`，避免把发射或飞行表现误当成受击表现；
4. 检查父级继承和是否存在形态覆盖；
5. 检查是否有随机后缀、等级后缀或运行时拼接规则。

### 阶段 B：资源解析

1. 根据路径规则确定实际 SWF；
2. 查找 Export / SymbolClass；
3. 记录 Character ID 与定义类型；
4. 展开根时间轴及全部嵌套依赖；
5. 标记 Bitmap、Shape、Sprite、Sound 和清除帧。

### 阶段 C：版本比较

按以下优先级比较 2.5、3.4、GitHub 和测试包：

```text
配置调用
→ 实际 SWF 文件
→ SWF 哈希
→ Export / SymbolClass
→ 定义类型
→ 时间轴和帧内容
→ 位图/形状依赖
→ 游戏内实机画面
```

发现差异时，先报告证据，再决定是否修改。不能因为名称相同或工具退出码为 0，就直接认定导入成功。

### 阶段 D：导入前安全检查

如果确实需要将某个特效从测试包或 2.5 版本移入 GitHub，应先：

1. 备份当前运行文件和源文件；
2. 保留 Git 提交点，确保可以回滚；
3. 先在隔离目录处理；
4. 按定义实例和引用语义递归重映射 Character ID；
5. 回读检查是否有悬空引用或类型冲突；
6. 只处理一个武器或一个等级；
7. 通过静态检查后再进行游戏内实测；
8. 实测确认后，才考虑写回正式资源和提交。

## 八、证据等级与结论标准

建议按以下等级记录结论：

| 证据等级 | 说明 |
|---|---|
| A | 配置调用、实际 SWF、帧图、哈希和游戏画面均相互印证 |
| B | 配置、SWF 结构和导出帧已确认，但尚未完成游戏内实测 |
| C | 只确认配置或导出名称，尚不能确认最终画面 |
| D | 仅凭文件名、中文名称或 Character ID 推测 |

只有达到 A 或至少 B，才适合把某个文件标记为“已确认受击特效”。D 级信息只能作为搜索线索，不能作为修改依据。

## 最终原则

```text
先找调用，再找资源；
先确认归属，再比较画面；
先展开时间轴，再判断帧数；
先核对内容，再判断版本；
先剥离挂点标记（basePoint/shootPoint 等命名实例，FFDec 静态导出渲染成逐帧静止的方框加号/圆形加号，任意配色；实机 2.5/3.4/新版均被 SWFLoaderManager 按名隐藏），再比较外观——标记是功能锚点不是美术本体、也不是版本差异；
先隔离验证，再修改正式文件。
```
