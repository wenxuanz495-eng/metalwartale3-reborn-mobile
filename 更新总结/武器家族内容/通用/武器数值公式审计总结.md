# 武器数值公式审计总结

> 审计日期：2026-09-05  
> 目的：记录“能量上限从 98 变成 196”的代码原因，并整理其他可能造成“面板值与实战值不一致”的公式。

## 一、能量上限为什么会乘 2

当前版本的武器数据初始化位于 `ArmsItemsData.as`，核心代码为：

```actionscript
this.maxEnergy = 2 * this.baseEnergy * (this.add.energy_max + 1);
```

其中：

- `baseEnergy` 来源于武器的 `energyUse` 基础数据；
- `add.energy_max` 是武器形态或附加数据提供的能量上限加成；
- `energy_max = 0` 时，公式仍然保留最前面的 `2` 倍换算。

因此，若武器定义层显示的基础能量为 98，运行时会得到：

```text
2 × 98 × (0 + 1) = 196
```

这不是单个武器的数据错误，而是当前版本 `ArmsItemsData` 对武器能量上限统一采用的运行时换算。2.5 参考版本的对应逻辑没有这个前置 `2 *`，所以同一份基础数值在两个版本中的运行结果不同。

## 二、这个公式适用于哪些武器

该公式写在武器数据类的公共初始化逻辑中，作用对象是所有经过 `ArmsItemsData` 创建、并使用这套能量系统的武器，而不是某一个指定家族。

适用条件可以概括为：

1. 武器使用 `ArmsItemsData` 的能量字段；
2. 武器已经完成 `baseEnergy` 和 `add.energy_max` 的数据初始化；
3. 运行时读取的是 `maxEnergy`，而不是只读取武器配置界面中的原始 `energyUse`。

`add.energy_max` 只负责额外增加倍率项的数值；即使它为 0，前置的统一 `2` 倍仍然存在。

目前没有发现第二个对所有武器再次统一乘 2 的公共公式。因此，98→196 的主要原因应直接归因于这里的运行时换算，而不是某个武器家族单独重复计算。

## 三、为什么测试包更容易一次性导入

测试包中的武器、ID、形态关系和特效引用本来就是在同一套测试目录结构中整理并验证的，导入时通常能够同时满足：

- 武器数据路径一致；
- 形态 ID 与特效 ID 的对应关系一致；
- 依赖文件位于预期目录；
- 同一版本的公共资源和脚本能够被一起加载。

因此，测试包一次性导入成功，说明这套文件组织和导入方法本身具有参考价值。但它不能证明直接复制到 GitHub 仓库时一定成功：GitHub 版本可能已经有不同的 ID 占用、文件结构、依赖引用或脚本版本。导入 GitHub 前仍需先做 ID 和路径冲突检查。

## 四、其他已经发现的类似“定义值/运行值”差异

### 1. 能量回复速度

实际回复由 `maxEnergyRate / 6` 驱动。当前 `INIT.FPS = 30`，而 `timer5 = XTimer(5)` 实际上每秒调用 6 次，因此运行中的总回复比例约等于 `maxEnergyRate`。

装备界面的百分比显示基本合理，但定义界面使用：

```text
energyRate × 30
```

来显示“点/秒”。这会造成定义界面上的数值看起来像每秒能量点数，例如 `0.011` 显示约 `0.3`，但它与实际能量点回复并不是同一个单位。这里属于显示单位或换算口径不一致，不是能量上限的第二个 `×2`。

### 2. 射速

面板射速使用 `attackGap + 0.067` 进行估算；实战射击则由 `ArmsAttack.attackPan()` 的按帧状态机控制。

因此，面板射速不一定等于真实发射频率。火神炮此前的实测结果就是：

- 面板约为 14.9 发/秒；
- 实战约为 7.5 发/秒。

这说明射速需要结合 Flash 动画帧、攻击状态和实际触发发射的帧间隔判断，不能只看武器介绍或面板公式。

### 3. 伤害与 DPS

面板使用 `getAllDataHurt()` 计算理论伤害；实际子弹则携带 `d.hurt`，并继续受到全局攻击加成、暴击、装甲属性等因素影响。

连锁子弹、闪电、激光、多段射击等特殊攻击还可能使面板理论值与单次命中或实战 DPS 不一致。因此这部分目前属于待逐类验证的风险点，不能直接套用面板数值作为实战结论。

### 4. `dpsHurt` 更新时机

当前版本 `ArmsItemsData.fleshData()` 中，`dpsHurt` 在 `define.fleshData()` 之后更新；2.5 版本则在之前更新。这个顺序可能造成一次刷新延迟，但目前没有证据证明它必然导致实战伤害错误，需结合具体武器进一步验证。

## 五、已排除的“类似乘 2”公式

以下代码中的乘 2 有明确的局部用途，不能与武器能量上限的统一换算混为一谈：

| 位置或用途 | `×2` 的含义 | 是否属于武器能量上限问题 |
| --- | --- | --- |
| 敌人困难度伤害、经验 | 难度或奖励设定 | 否 |
| 跟踪子弹速度 | 特殊追踪逻辑 | 否 |
| 训练值 `37×2` | 后续被 `/37/100` 抵消 | 否 |
| 出售价格 `/2` | 出售规则 | 否 |
| `V64` 固定点存储 | 内部编码，读写会抵消 | 否 |

目前未发现其他会对所有武器能量上限统一重复乘 2 的公共公式。

## 六、对后续导入工作的结论

1. 测试包的成品和导入流程有实际成功案例，具有较高参考价值，可以作为复制特效和武器配置的基准。
2. 将测试包成果导入 GitHub 仓库仍应按“文件结构 → ID 占用 → 依赖引用 → 运行验证”的顺序检查。
3. 2.5 与 3.4 之间不能只按数值或形态顺序机械对应；新增基础形态会改变旧形态的 ID 对照，蓄力特效也应沿用已确认的 3.4 对应规律。
4. 对能量、射速、伤害等数值，必须区分“配置/面板值”和“运行时实际值”。其中能量上限的 98→196 已经可以由代码确定，射速和特殊攻击则需要实战或逐帧验证。

## 七、火神炮芯片拦截决定

火神炮使用独立备弹规则，按照已确定的推荐方法处理：普通芯片、特殊芯片和紫色芯片全部禁止对 `fireFairy` 家族提供 `energy_max`（能量上限）和 `energy_rate`（能量回复）加成；芯片的其他属性继续生效。

拦截位置采用 `ArmsItemsData.fleshData()` 中的芯片属性合并阶段，只对 `fireFairy` 家族过滤，不修改全局芯片合并逻辑。火神炮能量上限现使用：

```text
火神炮能量上限 = 已解锁主武器格子数量 × 100 - (已装备主武器数量 - 1) × 100
```

本次已完成芯片能量属性拦截、火神炮能量上限规则，并已实现玩家火神炮的实际射速倍率：一连装为原始实战速度，二连装为 2 倍，三连装为 3 倍，四联装为 3.5 倍。实现位于 `ArmsAttack.attackPan()` 的玩家专用帧累积器分支，不修改 `shootNum`、`bulletNum`、面板射速公式或其他武器。射速数值仍需实机确认。
