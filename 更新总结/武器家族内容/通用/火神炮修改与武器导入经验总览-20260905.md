### 2. 火神炮能量上限公式

当前采用的公式为：

```text
火神炮能量上限
= 已解锁主武器格子数量 × 100
  −（已装备主武器数量 − 1）× 100
```

等价写法：

```text
（已解锁主武器格子数量 − 已装备主武器数量 + 1）× 100
```

其中 `已装备主武器数量` 包含火神炮自身。当前代码还保留最低值保护，计算结果低于 100 时按 100 处理。

示例：

| 已解锁格子 | 已装备主武器 | 火神炮能量上限 |
|---:|---:|---:|
| 4 | 1 | 400 |
| 4 | 2 | 300 |
| 4 | 4 | 100 |
| 8 | 1 | 800 |
| 8 | 4 | 500 |
| 8 | 8 | 100 |

### 3. 芯片能量属性拦截

用户要求火神炮不受任何芯片增加能量回复或能量上限的影响，包括：

```text
普通芯片
特殊芯片
紫色芯片
```

当前实现位于：

```text
D:\superalloy\metalwartale3-reborn.git\decompiled\gamefile\scripts\gameAll\data\ArmsItemsData.as
```

实现位置是 `fleshData()` 的芯片属性合并阶段，判断条件为火神炮家族：

```actionscript
this.define != null && this.define.id == "fireFairy"
```

对所有芯片来源过滤：

```actionscript
add1.energy_max = 0;
add1.energy_rate = 0;
add2.energy_max = 0;
add2.energy_rate = 0;
```

其中：

- `holeArr` 中的普通或特殊芯片属性会被过滤；
- `chipHole` 中的紫色芯片属性会被过滤；
- 芯片的其他属性继续生效；
- `addSelf` 是武器自身附加属性，不属于芯片，仍按原逻辑保留；
- 过滤只针对 `fireFairy`，不会改变其他武器的全局芯片规则。

### 4. 通用武器能量公式与火神炮的区别

非火神炮武器仍使用 `ArmsItemsData.fleshData()` 中的通用公式：

```actionscript
this.maxEnergy = 2 * this.baseEnergy * (this.add.energy_max + 1);
```

因此基础能量从 98 变为 196 的原因是运行时统一的前置 `2 *`，不是某个芯片重复加成。火神炮已经在同一位置使用独立的槽位/装备数量公式。

能量自动回复的调用位置为：

```text
D:\superalloy\metalwartale3-reborn.git\decompiled\gamefile\scripts\gameAll\data\GameData.as
```

`dataTimer()` 中的核心调用为：

```actionscript
id0.addEnergy(id0.maxEnergyRate / 6);
```

因此能量上限和能量回复必须分开检查，不能因为芯片拦截了 `energy_rate` 就认为所有回复路径都被删除。

## 五、火神炮实际射速系统

### 1. 代码路径

```text
D:\superalloy\metalwartale3-reborn.git\decompiled\gamefile\scripts\body\attack\ArmsAttack.as
```

这里是武器实际攻击状态机和子弹生成入口，不是武器介绍文本。

### 2. 当前实现的核心逻辑

当前火神炮玩家专用分支使用帧累积器：

```actionscript
FIRE_FAIRY_BASE_PERIOD_FRAMES = 4
fireFairyFrameAccumulator
attackPanFireFairy()
getFireFairyShootMultiplier()
```

当前倍率目标为：

| 形态 | 当前实际射速倍率目标 |
|---|---:|
| 火神炮一连装 | 1 倍 |
| 火神炮二连装 | 2 倍 |
| 火神炮三连装 | 3 倍 |
| 火神炮四连装 | 3.5 倍 |

实现特点：

- 只对玩家 `HeroCarBody` 的火神炮生效；
- 通过游戏帧累积决定实际发射次数；
- 不修改 `shootNum`；
- 不修改 `bulletNum`；
- 不额外增加一次发射中的子弹数量；
- 不修改武器面板射速公式；
- 不影响敌方火神炮和其他武器。

### 3. 为什么不能只看面板射速

武器介绍或面板中的射速通常是由配置字段估算出来的，常见参考是 `attackGap` 加固定帧时间。实际射击则经过 `ArmsAttack.attackPan()` 的状态机、Flash 帧和 `INIT.FPS` 控制。

此前火神炮出现过：

```text
面板显示约 14.9 发/秒；
实战实际约 7.5 发/秒。
```

所以射速修改完成后必须实机计时或逐帧计数，不能用武器介绍中的数字直接作为结论。

## 七、2.5、3.4 与当前版本的对应规则

3.4 新增形态不一定在旧形态 ID 后面顺序追加，有时会占用 2.5 的基础 ID，使 2.5 的旧基础形态在 3.4 中对应更高级形态。

已确认需要特殊处理的家族包括：

```text
异端审判
普罗米修斯
星爆
```

对应策略：

- 先按形态名称、家族 ID、导出名和实际时间轴建立映射；
- 2.5 的 LV1 可能对应 3.4 的 LV1～LV3；
- 2.5 的 LV3 可能对应 3.4 的 LV5；
- 以后新增 LV6、LV7 时，可按 3.4 的规律继续使用 LV5 特效；
- 恶魔牙、深渊 MK2 等纯新增形态，通常沿用上一形态特效；
- 蓄力特效不强行重新制作，优先沿用已验证的 3.4 对应关系。

因此不能机械执行“当前 LV1 直接替换为 2.5 LV1”，也不能只按 Character ID 相等进行迁移。

## 八、武器特效导入标准流程

标准流程文档：


黄金恶魔牙的专项问题记录：


### 1. 先隔离，再导入

每个家族在测试包建立独立目录，保留 `input`、`work`、`output`、`manifest`、`logs` 和 `report`。正式仓库不能直接作为实验目标。

### 2. 确认实际运行入口

先确认 `arms`、`sub`、`bullet` 实际加载的 SWF，以及测试启动使用的 `game.swf`。不能只根据文件名判断，因为旧版 `sub37.swf` 在当前项目中可能改名或由其他资源承担同一运行入口。

### 3. 导出 XML 并记录哈希

使用 FFDec 将来源和目标 SWF 导出为 XML，输入文件只放在测试目录的 `work` 中，同时记录 SHA-256。

### 4. 定位 SymbolClass 并建立依赖闭包

找到目标 Export 对应的根 Character ID，然后递归收集完整依赖：

```text
DefineSprite / MovieClip
DefineShape
DefineBits / 位图
PlaceObject、RemoveObject、ShowFrame
矩阵、颜色变换、边界、注册点
Sound、StartSound
SymbolClass 映射
```

不能只复制 PNG，也不能只复制根 Sprite，否则容易丢失帧动画、矩阵、注册点、声音和清理逻辑。

### 5. 全量重映射 Character ID

先读取目标 SWF 的最大 Character ID，再为来源依赖闭包分配目标中未占用的新 ID，并同步重写所有引用：

```text
Sprite 子标签引用
PlaceObject 引用
Shape 的 BitmapFill
声音引用
递归依赖
SymbolClass 导出 ID
```

Character ID 必须和定义类型一起判断。`DefineShape`、`DefineSprite`、`DefineSound` 等不能仅按数字互换。

### 6. 合并时间轴时保持当前定位

需要混合本体和旧版特效时，常见策略是：

```text
当前本体层
+ 旧版蓄力层
+ 旧版开火层
+ 当前 basePoint / shootPoint
```

逐帧核对帧数、深度、矩阵平移、缩放、注册点、声音、`RemoveObject` 和特效清理。不能让旧特效占用当前武器的注册点深度。

### 7. 只改目标配置区块

导入资源后，只修改目标家族的配置字段，并再次核对：

```text
imgLabel
bulletImgLabel
hitImgLabel
attackType
bulletSpeed
bulletLife
bulletWidth
attackGap
recoilValue
bulletVra
tranArr
```

除非用户明确要求，不要因为恢复视觉特效而自动改变伤害、速度、能量、射速或升级关系。

### 8. 重建、回读、独立运行

标准验证链：

```text
swf2xml
→ SymbolClass 定位
→ 递归依赖闭包
→ Character ID 全量重映射
→ 时间轴合并
→ xml2swf
→ swf2xml 回读
→ dumpSWF
→ 测试包独立运行
→ 游戏内验证
```

`xml2swf` 退出码为 0 只代表工具成功生成 SWF，不代表游戏内一定正确。必须检查回读 XML、导出名、帧数、深度、矩阵、嵌套引用和游戏画面。

## 九、已经暴露的导入陷阱

### 1. 测试包成功不等于正式仓库可以原样覆盖

测试包较容易一次性成功，是因为其武器、形态、ID、依赖和运行入口在同一套目录内被一起整理过。正式仓库可能已经存在：

```text
不同的 Character ID 占用
不同的 SWF 资源入口
不同的 SymbolClass
不同的版本形态顺序
不同的脚本或配置字段
```

因此测试包是基准案例，不是免检查的整体补丁。

### 2. Character ID 被占用或类型冲突

不要直接复制来源的 Character ID。必须记录：

```text
来源文件
旧 Character ID
定义类型
Export / SymbolClass 名称
引用关系
目标文件中的新 Character ID
```

只要资源闭包中有 ID 冲突，就需要整体重映射依赖，而不是只给根节点换一个数字。

### 3. 只看工具回读会产生假成功

必须同时检查：

- 根 Symbol 是否存在；
- 本体和子弹帧数是否完整；
- 蓄力、开火和消退层是否存在；
- `shootPoint`、`basePoint` 和矩阵是否正确；
- 声音和嵌套资源是否仍被引用；
- 游戏内是否真正显示目标效果。

### 4. 写盘时不能重新读取原始 XML

鞭炮/黄金鞭炮实验确认过一种严重错误：脚本在内存中完成了导入、替换和 ID 重映射，但写出 `merged.xml` 时又重新读取原始 `target.xml`，导致修改全部丢失。以后必须：

```text
保留同一个 ElementTree 对象
→ 所有合并操作都修改该对象
→ 直接把已修改对象写入 merged.xml
→ 写盘前检查关键导出、帧数和 ID
→ xml2swf 后再次 swf2xml 回读
```

### 5. 帧数不等于可见画面帧数

检查特效时要分别记录：

```text
时间轴总帧数
可见帧数
清理帧
静态变体数量
```

清理帧、透明结束帧和移除对象的帧不能直接判定为多余帧。

### 6. 挂点标记不是美术本体（2026-09-08 电磁炮家族补记）

武器本体 sprite 时间轴里可能存在 `basePoint`/`shootPoint` 命名挂点实例，FFDec 静态导出里渲染成醒目的**挂点标记**（方框加号或圆形加号，红/白/黑/透明任意配色，逐帧位置静止；实机 2.5/3.4/新版均被 `SWFLoaderManager` 按名隐藏，标记不代表任何版本的实机观感）。它们是射点/基点功能锚点，不是美术本体：比对老版本帧图时勿把红色标记当成炮体配色或待机动画，回迁时也不作为美术对象。判定法与操作细节见《武器视觉效果构成元素键》A1/C1 与 `tmp-soya-family-test\武器特效导入标准流程.md` 12.4 节；实证记录见 `..\副武器家族\电磁炮家族\特效复古任务\电磁炮家族2.5-3.4-11.3检查审计-20260908.md` 第三节。

## 十、黄金恶魔牙案例的经验
