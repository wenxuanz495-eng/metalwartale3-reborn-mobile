# 更新总结 · 总索引

> 定位：本目录归档游戏**所有更新的任务总结**——每次功能、回迁、修复做完后，把"改了什么、怎么验证的、还剩什么"写成 MD 存放在这里，让后续维护者有架构可循。
> 分工边界：工程规则与架构文档在 `docs\`；玩家可见的更新说明在发行包 `游戏更新公告.txt`（3.0 起由 `公告.txt` 更名，致谢单列为 `感谢公告.txt`）；过程性工作区（中间产物、测试包）不入库，只把最终版总结和关键脚本/证据图收进来——历史工作区 `tmp-soya-family-test\` 已于 2026-09-15 整体移入冷备，现位于 `F:\超合金冷数据备份\TMP\端游端\工作区归档-tmp-soya-family-test\`（F 盘冷备已于 2026-09-21 整体重排为"分端 → 版本分段"结构）。

## 新更新怎么归档（规则）

1. **选位置**：
   - 围绕某个武器家族的改动（特效回迁、家族数值、家族 bug）→ `武器家族内容\主武器家族\<家族名>\` 或 `武器家族内容\副武器家族\<家族名>\`
   - 功能性新功能（新增玩法、界面功能等）与非家族内容调整（如文案/署名清理）→ `功能性更新总结\`
   - 跨武器的系统级改动（界面、存档、商城、公会、启动器、构建流程）→ `版本更新总结\<版本号>更新\`，没有对应文件夹就按版本号新建
   - **新建武器/新形态/新导出名**类任务（画师新捏素材、新增等级或名字，不回迁旧素材）→ 总结归 `新建武器（形态）方法总结\`；过程性执行记录仍归所属家族文件夹
   - 服务端/启动器/引擎基础设施等**非游戏内容的底层维护**（日志通道、上报管线、进程管理等）→ `开发商维护\`
   - 已规划未做完 → `未完成重点任务\`；完成后移出到对应分类，不在两处重复存放
2. **命名**：`主题-YYYYMMDD.md`（日期用完成日）；对比图 `主题对比图-YYYYMMDD.png`；回迁/合并脚本用可读英文名（如 `plasma_restore_merge.py`）
3. **总结 MD 必备四段**：目标、实际修改（改了哪些文件+代码/资源锚点）、构建与验证（哈希、回读、像素比对等证据）、待实机确认项
4. **移除资源必须留备份**：在对应家族/分类文件夹下建 `备份-移除的孤儿资源-YYYYMMDD\`，存放移除前完整副本、渲染存档和 README 说明（范例见 `武器家族内容\主武器家族\等离子炮家族\备份-移除的孤儿资源-20260907\`）；长期确认无用途后可整体删除
5. **更新索引**：归档后同步更新所在分类的 README（`武器家族内容\README.md` 的家族清单和"本轮变更清单"；`版本更新总结\` 按版本号建子文件夹，并在 `版本索引.md` 追加该版本一行）；**每封装或发布一个版本，必须在本目录 `版本索引.md` 登记**（版本号 / 日期 / 类型 / GitHub tag 与 Release / 双包 SHA-256 / 关联总结）
6. **提交**：总结归档与代码修改分开或合并提交均可，但必须在同一次推送内，保证"代码到了 GitHub、总结也到了"
7. **错误收集**：执行中实际遇到的通用错误/异常（工具、解析、部署、环境），记入 `错误收集/`，每条备注出现场景（任务·步骤·环境）；家族强相关的执行错误与查证方法可沉淀在 `武器家族内容\通用\` 相关子文件夹（`相关错误经验总结\`、`原版武器相关资料总结\`），家族合并语义陷阱仍留在家族/通用总结内
