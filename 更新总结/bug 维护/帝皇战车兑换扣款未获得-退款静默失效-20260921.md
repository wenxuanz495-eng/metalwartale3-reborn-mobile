## 二、根因（两段叠加）

**（1）扣款在前、前置校验在后** —— `UI/shop/OneExchangeUI.as`

- `onBuyClick()`（`:395`）**先扣款**：`:436` `this.GD.propsItems.useItemsNum("justice_badge",ed.EPayCount)`（150 枚）；
- **之后**才校验前置：`:455-457` `if(gd.name == "帝皇战车" && !this.CheckCarHas("dihuang"))` → 未集齐 5 辆即走失败分支；
- 失败分支（`:459-467`）弹提示、`_tempDT.flag = 0`，然后尝试"退款" `:463 this.GD.propsItems.useItemsNum("justice_badge",-ed.EPayCount)`，`return`。

**（2）退款在"余额刚好花光"时静默失效** —— `gameAll/data/GoodsItemsDataGroup.as`

- 扣款侧 `useItemsData(id, 150)`（`:472-486`）：当 `id.nowNum == num0`（**恰好相等**）时执行 **`delItemsData(id)`，把整条物品记录从数组删除**；
- 退款侧 `useItemsNum(..., -150)`（`:507-524`）：`num0 != -1`，于是 `getItemsByBase("justice_badge")`（`:416-427`，**要求 `nowNum >= 1` 才返回**）→ 记录已被删 → 返回 `null` → `if(gid0 != null)` 不成立 → **`return false`，无任何 trace，退款落空**。

### 触发条件（余额三档）

| 扣款前余额 | 扣款后 | 退款 | 结果 |
|---|---|---|---|
| > 150 | 仍有剩余，记录保留 | 成功（数值加回） | **无损**，仅看到提示 |
| **= 150** | 记录被 `delItemsData` 删除 | `getItemsByBase` 返回 null → **落空** | **丢 150 荣誉勋章、无车、无异常提示**（本次报告的情形） |
| < 150 | 按钮显示"荣誉勋章不足"且不可点（`setCanBuyBtn` `:311-314` 门槛） | — | 走不到扣款 |

"攒到刚好够价"是这类玩法最常见的状态，故命中率不低。

## 三、修复方案与决策点

用户裁定（2026-09-21）：手动修复；按"主修 + 加固"一起做。

| # | 改动 | 说明 |
|---|---|---|
| R1 | 新增字段 `_tempMaxI` | 跨 `onBuyTips → onBuyClick` 传递本次**已抽中**的奖品下标 |
| R2 | **前置校验前移**（主修） | 把"帝皇战车需集齐 5 辆"校验移到 `onBuyTips` 内、**扣款之前**，与既有 `gd.type == "sub"`"只能兑换一次"预检同处；命中即提示并 `return`，**永不扣款**（提示文案与原失败分支逐字一致） |
| R3 | `onBuyTips` 记录抽中下标 `this._tempMaxI = maxI;` | 紧接 `this._tempDT = dt;` |
| R4 | `onBuyClick` **不再二次抽奖** | 改用 `_tempMaxI`（缺失/越界时回退为原地抽一次，保留兜底）。原实现只在 `onBuyTips` 抽一次用于预检，`onBuyClick` 又重新抽一次决定实际发放 → "确认依据的奖品 ≠ 实际发的奖品"、`sub`"只能兑换一次"拦截判据与实际发放不一致；R2 的正确性也依赖 R4（否则预检判的与实际发的可能不是同一个奖品） |
| R5 | 失败路径退款改为 `this.refundPay(ed)` | 按付款渠道对称退款，不再写死荣誉勋章 |
| R6 | 新增 `refundPay` / `refundItems` 两个私有方法 | ①按 `EPayType` 对称退款（金币/超合金X/超合金Y/荣誉勋章）；②**记录已被扣空删除时补建**（`addItems`，`newB=false`）而不是走"改数值"路径；③`materialsItems` 在 `modCraftFree` 下未真实扣款则跳过退款（避免凭空造物）；④失败/补建均 `trace` 留痕 |
| R7 | 新增 `import gameAll.data.GoodsItemsDataGroup;` | `refundItems` 形参需要该类型名 |

**保留未改**：失败分支的前置校验仍留在 `onBuyClick`（R2+R4 后实际不可达，作为纵深防御保留）；手游既有的 `modPurchaseIgnoreConditions` 两处守卫维持原样。

## 七、遗留与决策点

1. **端游同缺陷未修**：`metalwartale3-reborn.git\decompiled\gamefile\scripts\UI\shop\OneExchangeUI.as` 同一逻辑（且**无** `modPurchaseIgnoreConditions` 守卫，`:427` 扣款后 `:451` 无条件退款）。端游同样具备"恰好花光即丢币"的条件，是否同步修复待裁定（两仓需各自改，不能整文件覆盖）。
2. **受害玩家补偿**：存档为本机 `superalloy_mobile_save`，需人工补发（补 150 荣誉勋章或直接补发帝皇战车）；补偿方案待用户裁定。
3. **`modPurchaseIgnoreConditions` 语义**：手游"购买无视条件"开着时，帝皇战车前置仍拦截（R2 后拦截点前移，行为与之前一致——仍拦截），且扣款/退款均被 mod 跳过。即该修改器项**既不免前置、也不扣钱**，语义待用户明确（要么真放行前置，要么明确定义为只管价格）。
4. **失败路径无上报**：本次仅在退款失败/补建时加 `trace`（进客户端日志），未接服务端上报通道。
