# VIP副本剩余时间退出仍触发冷却 · 排查与修复记录

> 记录日期：2026-09-20
> 状态：**已实施修复，待实机确认**
> 现象（用户报告，与黄金黑绳同批）：VIP副本有剩余时间的时候退出，仍然有冷却时间。

---

## 一、复现链（代码级推演）

1. **入场**：VIP 地图（`VipExtraLevel`）按 VIP 档位给时长 `mapTime`（30/60/90/120 分钟，`VipData.getMapDuration`），进入条件 `canEnterMap()` = 无冷却且 `mapTime > 0`。
2. **走时**：`VipExtraLevel.timeTimer`（每 1/6 秒）递减 `mapTime`；耗尽时置 `-100` 并 `exitEvent()` 踢出。
3. **退出**：`EventGroup.closeLevel`（`EventGroup.as:265-268`）对 `VipExtraLevel` **无条件**调用 `vipData.startMapCooldown()`。
4. **`startMapCooldown`**（修复前）：只要不在冷却中，就把 `mapTime` 清零并设 `mapCooldownReadyAt = now + 冷却时长`（20/15/10/5 分钟按档位）——**提前退出时剩余时间被清零且进入冷却**。

VipUI 面板文案"退出后冷却：X分钟"（`VipUI.as:242/324`）是旧设计的表述，与用户裁定的新行为相悖。

## 二、根因

冷却的唯一触发点是 `closeLevel` 的无条件调用；`startMapCooldown` 自身没有"时间已耗尽"前置条件，导致"退出"与"耗尽"两种场景被同等惩罚。设计本意（对照 `refreshMapAccess` 的"legitimately exhausted map always has a future cooldown timestamp"注释）是冷却作为**时间耗尽**的惩罚，而非退出的惩罚。

## 三、修复方案与决策点

用户裁定（2026-09-20）：有剩余时间退出不应有冷却。

- **`VipData.startMapCooldown` 增加前置条件 `mapTime <= 0`**（与该方法既有的 `seconds > 0`、`不在冷却中` 前置同型）——冷却=耗尽惩罚成为数据层不变量，任何调用方（现存唯一调用 `closeLevel`）自动继承；
- 提前退出时 `mapTime` 保留，`canEnterMap` 立即为真，可马上重入续用剩余时间；存档字段 `mapTime` 原样持久化，`refreshMapAccess` 仅在超出时长上限时回卷，不受影响；
- **VipUI 文案同步**："退出后冷却中" → "冷却中"（2 处）、"退出后冷却" → "时间耗尽后冷却"（2 处），消灭误导表述；
- 覆盖面说明：战斗失败（gameFail）等一切经 `closeLevel` 的退出在 `mapTime > 0` 时一律不冷却、保留剩余时间——统一"冷却只属于耗尽"的规则；
- 自然耗尽路径不受影响：耗尽时 `mapTime` 已被置 `-100`（≤0），守卫放行，冷却照常启动。
