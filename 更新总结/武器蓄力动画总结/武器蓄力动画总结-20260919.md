## 二、★重大教训一：时间轴动画静止冻结（替换型放置不渲染）

**症状**：蓄力光球不变形、火焰三帧只显示第一帧、装填滑动永远看不见——动画"冻结"在首帧；而播放头探针证明帧号在正常前进。

**根因（引擎级）**：本引擎运行时对 PlaceObject2 的「同深度替换角色」静默不渲染——添加（空深度放置）与移除（RO）都正常，唯独"同深度换角色"不更新像素。逐帧动画若按直觉写成"同深度换图"，就只有第一帧可见。

**标准写法（红线）**：逐帧换图 = 上一帧角色 `RemoveObject2` + 本帧角色 `PlaceObject2`（RO 在前、放置在后，同帧完成）；位移/滑动用 MOVE 标签（placeFlagMove=1 无 characterId）。

**详见**：`..\新建武器（形态）方法总结\时间轴动画替换失效修复与标准写法\`（含修复前后对比证据图）。

**为什么当时误判"资源坏了"**：FFDec 自带渲染器同样不渲染替换帧（内部帧分割错乱），且其导出/回读又完全正确——**FFDec 的渲染结果不可作为裁决依据**（导出/回读可信，渲染不可信）。裁决只能靠游戏内探针。

## 三、★重大教训二：装填动画"永远看不到"的机制

早期版本装填滑动写在时间轴后段（f12~f14），但 `attackGap=0.4s` 下连续开火每 0.4s 就 `playOnce` 重启动画——播放头永远到不了后段，装填动画**结构性不可见**（用户"等很长时间才触发装填"的观感根源）。

**解法（V31/V34 定版）**：重型武器直接把动画做成完整周期——`attackGap ≥ 总帧数/30`，蓄力→发射→3 秒空膛→1.87s 滑装全部在周期内可达。轻武器若用后段装填，同理必须保证 attackGap ≥ 动画周期。

## 四、蓄力→发射的同步机制（配置耦合）

- `attackDelay`（秒）：攻击开始（playOnce 重启动画）到真子弹生成的延迟。**换算：蓄力帧数 ÷ 30**。当前蓄力 25 帧 → `attackDelay=0.85` → 真子弹在 f27 与出膛视觉同帧。
- `attackGap`（秒）：完整攻击周期，必须 ≥ 动画总帧数/30。
- `imgLoopTime=0`（保持）：走 imgAttackOnce 单次播放分支；禁止 imgAttackLoop（循环播放会打断"空膛→装填"的叙事）。

## 五、亚像素纪律（V44 教训）

部件2 归位期的教训：**该武器的一切微调均为亚像素级（低于一格），严禁整像素步进**。放置矩阵为 twips 精度（1px=20tw），微调一律按 **0.1~0.5px（2~10tw）粒度**执行。V44 的两次整像素移动过冲被当日撤回；V43 的 +2tw 亚像素右移经用户多次观察确认合格。已录入家族 README 已知注意事项。

## 六、诊断工具箱（冻结/错位类问题的标准排查链）

按序部署，每层缩小一半可能（前两层为游戏内探针，经 `api/client-log` 落盘 `build\saves\client_errors.log`）：

1. **播放头探针**：imageTimer 采样 `mc.currentFrame` → 区分"没在播"与"在播"。
2. **显示列表探针**：采样 `mc.numChildren` → 区分"标签未应用"与"已应用"。
3. **像素指纹**：`BitmapData.draw(mc)` 采样哈希 → 最终裁决"显示列表变了但像素没变"（= 渲染层问题）。
4. **渲染快照回传**：位图 base64 经 `api/client-log` 上传还原成图片——**最终裁决手段**，直接看到游戏画了什么。

配套基建与陷阱：

- 单条日志上限：服务端 `sanitizeLogField` 4000 字节 + 客户端 `Game.as escapeClientLog` 4000 字符（后者属高风险脚本，改动需 P-code 审批）——大体积回传用直连 POST 绕开；服务端上限已提至 65536（20260918）。
- **FFDec 渲染不可信**：其导出/回读正确，但帧渲染对替换型标签会漏画/错帧——文件正确性只用"导出+回读"验证。
- **GIF 截图会骗人**：GIF 去重编码会丢弃小面积变化帧，造成"动画静止"的假象——静止判断必须用逐帧像素差分或游戏内探针，不能凭 GIF。
- **F2 慢放**（stage.frameRate=1）是用户侧最有效的逐帧验收手段。

## 七、验证清单（每版必过）
